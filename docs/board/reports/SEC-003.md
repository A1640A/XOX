# SEC-003 — WS bileti tek kullanımlık

**Durum:** Tamamlandı (bkz. "Açık kalan" bölümü — kapsam dışı iki madde var, gerekçeli).
**Branch:** `feat/SEC-003`
**Commit:** `e46bd1bfcfed8786d98be31f4b991d225408fd2c`

## Özet

WS bileti (`POST /api/ws/ticket`) artık **tek kullanımlıktır**. Önceden bilet durumsuz bir
JWT'ydi — imza + `exp` geçerliyse TTL (30 sn) boyunca kaç kez WS'e bağlanmak için kullanılırsa
kullanılsın kabul ediliyordu. Çalınan bir bilet (URL query'sinde, log'da, referrer'da) artık en
fazla **bir** bağlantı açabiliyor; ikinci deneme `4401` alıyor.

## Mimari

- `packages/db/src/models/ws-ticket.ts` — yeni `WsTicket` koleksiyonu: `jti` (benzersiz),
  `userId`, `room`, `expiresAt` (TTL indeks, `mobileRefreshTokens` ile aynı kalıp), `usedAt`
  (`null` = tüketilmedi).
- `packages/db/src/tickets.ts` — `recordWsTicket` (ihraç), `consumeWsTicket` (tüketim),
  `revokeWsTicketsForUser` (signOut temizliği — bkz. "Açık kalan").
- `apps/web/lib/auth/tokens.ts` — `signToken('ws-ticket', ...)` artık her çağrıda `randomUUID()`
  ile yeni bir `jti` üretip JWT'ye gömüyor (`.setJti()`) ve `SignedToken.jti` olarak dışa
  veriyor. Fonksiyon overload'ları `kind:'ws-ticket'` iken dönen `jti`'yi TİP DÜZEYİNDE
  `string` (opsiyonel değil) yapıyor — çağıran taraf unutma riski taşımıyor.
- `apps/web/app/api/ws/ticket/route.ts` — bilet imzalandıktan hemen sonra `recordWsTicket`
  ile DB'ye `usedAt:null` kaydını yazıyor. DB yazması başarısız olursa 500 döner, **kullanılamaz
  bir bilet istemciye asla verilmez**.
- `apps/web/lib/auth/identity.ts` — `resolveIdentity`'nin `?ticket=` dalı, `verifyToken` (imza/
  aud/exp/room) geçtikten SONRA `consumeWsTicket(jti)` çağırır. `jti` claim'i yoksa (ör. bu
  mekanizmadan önce üretilmiş bir token) **fail-closed**: bilet reddedilir. `WS-001`'in upgrade
  route'una (`apps/web/app/api/rooms/[code]/ws/route.ts`) HİÇ DOKUNULMADI — bu dosya "Dokunma"
  listesindeydi ve tüketim mantığı zaten tek çözücünün (`resolveIdentity`) içinde, dolayısıyla
  hiçbir çağıranın değişmesi gerekmedi.
- `packages/shared/src/constants.ts:23` — yorum artık gerçeği anlatıyor: tek kullanımlık
  disiplin `WS_TICKET_TTL_SECONDS`'tan değil `consumeWsTicket`'ın atomik komutundan geliyor.

## Atomik tüketim — kod kanıtı

`packages/db/src/tickets.ts`:

```ts
export async function consumeWsTicket(jti: string): Promise<ConsumeWsTicketResult> {
  const now = new Date()
  const updated = await WsTicket.findOneAndUpdate(
    { jti, usedAt: null, expiresAt: { $gt: now } },
    { $set: { usedAt: now } },
  ).lean()
  if (updated !== null) return { ok: true }

  const existing = await WsTicket.findOne({ jti }).lean()
  if (existing === null) return { ok: false, reason: 'not-found' }
  if (existing.usedAt !== null) return { ok: false, reason: 'already-used' }
  return { ok: false, reason: 'expired' }
}
```

Filtre (`usedAt: null`) ve yazma (`$set: { usedAt: now }`) **aynı `findOneAndUpdate` komutunda**
— "oku, kontrol et, yaz" üç ayrı adım YOK. Bu, `casUpdateRoom`'un oda geçişlerinde kullandığı
aynı tek-komut disiplini (kart talimatındaki desen).

## Yeniden bağlanma KIRILMADI — analiz + kanıt

**Bulgu:** Web tarayıcı istemcisi (`apps/web/lib/client/use-room.ts`, `browserWsUrl()`) WS'e
**HİÇBİR ZAMAN `?ticket=` eklemiyor** — kimlik Auth.js oturum çerezi üzerinden geçiyor
(`resolveIdentity`'nin 2. önceliği, `allowTicket` gerektirmiyor). `onReauth`/`handleReauth`
(4401 sonrası backoff ile yeniden deneme) de salt `client.connect()` çağırıyor, ticket
istemiyor. Yani **bugünkü web reconnect akışı `?ticket=`'e hiç dokunmuyor** — bu görevin
değiştirdiği kod yoluyla ETKİLEŞMİYOR.

`apps/mobile` tarafında da bilet henüz kullanılmıyor (`grep -rl ticket apps/mobile` boş sonuç —
WS/oda ekranı mobilde henüz yazılmadı). Yani `?ticket=` bugün YALNIZCA `WS-001`'in upgrade
route'u tarafından `allowTicket:true` ile kabul ediliyor ama hiçbir gerçek istemci onu
otomatik-yenileme döngüsünde kullanmıyor — tek kullanımlık yapmanın kıracağı canlı bir akış
YOK.

## `Sec-WebSocket-Protocol` değerlendirmesi (kart talebi: DEĞERLENDİR ve RAPORLA)

**Sonuç: bugün mümkün değil, uygulanmadı.** Kanıt — kurulu `@vercel/functions@3.9.5`'in tip
tanımı:

```ts
// node_modules/.../@vercel/functions/websocket/index.d.ts
export interface UpgradeWebSocketOptions {
  maxPayload?: number
}
export declare function experimental_upgradeWebSocket(
  handler: (ws: WebSocket) => void | Promise<void>,
  options?: UpgradeWebSocketOptions,
): Promise<Response>
```

`options` yalnız `maxPayload` alıyor — el sıkışma yanıtına `Sec-WebSocket-Protocol` başlığı
KOYMANIN hiçbir yolu yok. RFC 6455 §4.1 gereği istemci `Sec-WebSocket-Protocol` gönderirse ve
sunucu yanıtında EŞLEŞEN bir alt-protokolü YANKI YAPMAZSA tarayıcılar bağlantıyı BAŞARISIZ
sayar (WHATWG WebSocket spesifikasyonu, "Fail the WebSocket Connection" adımı). İstek
başlığından bileti OKUMAK teknik olarak mümkün (`request.headers.get('sec-websocket-protocol')`
— kimlik zaten upgrade'den ÖNCE `Request`'ten çözülüyor), ama yankı yapamadan bu yola geçmek
TÜM tarayıcı bağlantılarını kırar.

**Öneri:** URL query string'de kalınsın; sızıntı yüzeyi bu kartla (tek kullanımlık) zaten
"bir bağlantı"ya indirildi. `SEC-004` (`?ticket=` log maskelemesi) ayrı kart olarak dursun.
`@vercel/functions` ileride `protocols`/`selectProtocol` gibi bir seçenek eklerse (şu anki
sürümde yok) bu karar yeniden değerlendirilebilir.

## Açık kalan (kapsam dışı, gerekçeli)

**signOut ticket iptali:** Kart, çıkışın (`signOut`) elde duran (henüz tüketilmemiş) bileti de
iptal etmesini istiyor. Bunun için gereken TEK satır (`revokeWsTicketsForUser(userId)`) yazıldı
ve test edildi (`packages/db/src/tickets.test.ts` → `revokeWsTicketsForUser` describe bloğu, 3
test) ve `@xox/db`'den export edildi — ama çağıracağı yer Auth.js'in `events.signOut`
kancasıdır, ki bu `apps/web/auth.ts`'te tanımlanır. `auth.ts` bu görevin "Çakışma kümen"
listesinde YOK ve genel yazma alanımın (`apps/web/app/api/**`, `apps/web/lib/**`,
`packages/db/**`) da dışında — dokunmadım. **Lead'e:** `auth.ts`'e (ya da onu saran bir
sarmalayıcıya) şu satırın eklenmesi gerekiyor:

```ts
events: {
  async signOut(message) {
    const userId = 'token' in message ? message.token?.sub : message.session?.userId
    if (userId !== undefined) await revokeWsTicketsForUser(userId)
  },
},
```

Bu satır eklenene kadar: çıkış yapan bir kullanıcının HENÜZ BAĞLANMAMIŞ (tüketilmemiş) bileti
TTL'i (30 sn) dolana kadar teknik olarak geçerli kalır — ama artık en fazla BİR bağlantı açar
(bu kartın asıl kazanımı), süresiz devralmaya dönüşemez.

**`?ticket=` log maskelemesi (SEC-004):** `apps/web/lib/log.ts` bu görevin yazma alanı dışında;
bilet BİÇİMİ (hâlâ imzalı bir JWT string'i, `?ticket=` query param'ı) değişmedi, dolayısıyla
mevcut maskeleme varsayımlarını bozmadım. SEC-004 ayrı kart olarak açık kalmaya devam ediyor.
